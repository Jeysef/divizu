Overview

A divizu document is a list of blocks. A block is a container, service, adapter, or port. Blocks declare sockets for the interfaces they need, and a socket may name the block that provides that interface. The provider plugs into the socket.

The layout reads bottom-up: the composition root sits at the bottom, its sockets open upward, and implementations sit above it. Multiple unplugged roots are laid out side by side as a forest.

Nothing is measured at runtime. Character widths are estimated from a monospace grid, so the same DSL produces byte-identical SVG on every machine.

Roles & colors

Role colors are applied to the block outline. The palette adapts to light and dark themes; the swatches below show the light defaults.

root The composition root / baseplate. Sits at the bottom with a bottom-left title.
composite A container that hosts sockets and modules. Inferred for socket-bearing blocks.
service A provided service or factory. Same blue as composite, different intent.
adapter A leaf implementation. Inferred for blocks with no sockets or candidates.
port An interface boundary / port marker when the distinction matters.

Roles are optional. A socket-less block with no candidates defaults to adapter; a socket-bearing block defaults to composite.

Sockets & plugs

A socket is a U-shaped notch cut into the top edge of a block. Its width comes from the port name. An interface pill sits on the floor of the notch.

  • socket PaymentPort <- StripePayment is a bound socket: a solid purple pill names the interface, and StripePayment is drawn above the socket.
  • The provider's bottom edge grows a tab (the plug). The tab descends into the notch and stops just above the interface pill.
  • The child body is centred on the socket and sits a small fitGap above the parent's top edge (default 10px), which keeps the strokes visually clear.
  • Every block perimeter — top notches, body, bottom tab — is one clockwise polygon rounded with a single quadratic-curve pass.

A block may have several sockets. They are ordered left-to-right, and each socket reserves an envelope as wide as the wider of its own notch and the provider's whole subtree. Wide subtrees therefore push their neighbouring sockets outward instead of covering them.

The anti-shadowing rule is the reason a wide child never hides a sibling port. Left and right extents are reserved independently, so asymmetric subtrees stay honest too.

Unbound sockets

Write a socket without a provider to leave it unbound: 

CheckoutApi {
  socket ShippingPort
  socket OrderUseCase <- OrderService
}

An unbound socket has no child block. Its interface pill is drawn with a dashed outline and muted purple fill. It still carves a real notch, so it participates in layout exactly like a bound socket.

Use unbound sockets for dependencies that live outside the diagram, for ports that cross a bounded context, or to deliberately stop a graph at an interface boundary.

Internal modules

modules: lists collaborators that are internal to a block, not separately plugged dependencies. They render as compact horizontal rows inside the block body, below the sockets. Extended names are fine; quote a name if it contains a comma. 

OrderService "composite" {
  role: composite
  modules: OrderValidator, PricingEngine, OrderMapper
}
  • Modules do not create nodes, sockets, or layout edges.
  • Root containers are intentionally empty: modules on a root are ignored.
  • Quote a name to include a comma: "conn pool, primary".
  • A module list may continue on the next line when the line ends with a comma.

Candidates with side notches

candidates: lists alternative implementations that a factory or service can produce. Candidates share the same vertical card rendering as modules, but they mean “one of these”, not “all of these”. 

PreviewGeneratorFactory "factory" {
  role: service
  socket ImageScaler <- SharpImageScaler
  candidates: DocumentPreview, ImagePreview(ImageScaler), VideoPreview
}
  • Name renders a plain rounded card.
  • Name(RequiredInterface) cuts a U-shaped notch into the card's right side and places a rotated interface pill inside it. It means that candidate itself requires RequiredInterface.
  • A candidate side notch is not a top-edge socket. It does not bind a provider, create a child node, or add a layout edge.

The full working example is examples/candidates.di. It shows two factories, ImagePreview(ImageScaler) and AwsStorage(Encryption), with side notches.

DSL reference

The complete grammar:

BlockId ["subtitle"] {
  role: root | composite | service | adapter | port
  modules: name, "name, with comma", name
  candidates: Name, Name(RequiredInterface), Name
  socket PortName
  socket PortName <- ProviderBlockId
}
SyntaxMeaning
BlockId "subtitle" { ... } Declares a block. Ids may contain letters, digits, _, ., and -. Subtitles are optional.
role: ... One of root, composite, service, adapter, port.
modules: a, b Internal collaborators rendered as compact horizontal rows.
candidates: A, B(IFace) Alternative implementations; the optional argument adds a side notch and rotated pill.
socket Port Unbound dependency: dashed pill, no provider.
socket Port <- Provider Bound dependency: solid pill plus a provider plug.

Details

  • # and // start a comment outside quoted strings.
  • Angle brackets are tolerated: socket <Port> <- <Provider>.
  • Blank bodies are valid: Leaf {}.
  • Modules continue across lines when the line ends with a comma.
  • Block ids must be unique; socket references must resolve.
  • The graph must be acyclic and every block must be reachable from a root.

Validation is intentionally strict. Duplicate ids, unknown roles, unknown providers, unreachable blocks, and cycles fail with a readable error instead of producing a misleading diagram.

Examples

Checkout — root, composite, adapters

CheckoutApi "DI container (root)" {
  role: root
  socket ShippingPort
  socket OrderUseCase <- OrderService
  socket ReportPort
}

OrderService "composite" {
  role: composite
  modules: OrderValidator, PricingEngine, OrderMapper
  socket PaymentPort <- StripePayment
  socket StockPort <- PostgresStock
  socket NotifyPort <- EmailNotifier
}

StripePayment "adapter" {
  role: adapter
}

PostgresStock "adapter" {
  role: adapter
  modules: "conn pool", migrations
}

EmailNotifier "adapter" {
  role: adapter
}

Candidates — factories with side notches

UploadRequest "root" {
  role: root
  socket Scanner <- ThreatProtectScanner
  socket ImageScaler <- SharpImageScaler
  socket PreviewGenerator <- PreviewGeneratorFactory
  socket Storage <- StorageFactory
}

PreviewGeneratorFactory "factory" {
  role: service
  socket ImageScaler <- SharpImageScaler
  candidates: DocumentPreview, ImagePreview(ImageScaler), VideoPreview
}

StorageFactory "factory" {
  role: service
  socket Encryption <- AESEncryption
  candidates: S3Storage, AwsStorage(Encryption), WebDavStorage
}

Source files: checkout.di, candidates.di. Open either one in the playground to edit it live.

CLI & API

Render a file to SVG, or read the DSL from stdin:

diviz <input.di> [options]
cat graph.di | diviz [options]
OptionDescription
-o, --out <file>Write SVG to a file (default: stdout)
-t, --theme <mode>auto, dark, or light (default auto)
-p, --padding <px>Canvas padding (default 56)
--radius <px>Corner radius (default 10)
--fit-gap <px>Edge-to-edge plug gap, 4–20 (default 10)
--socket-gap <px>Space between socket envelopes (default 28)
--responsiveEmit width="100%" height="100%"
--title <text>Accessible SVG title
--jsonPrint computed layout geometry instead of SVG
-w, --watchRe-render when the input file changes

Use it as a library:

import { render, mount, layout, parseDSL } from "diviz";

const { svg, width, height } = render(dsl, {
  theme: "dark",
  padding: 48,
});

mount(document.querySelector("#di"), dsl, { theme: "light" });

// Geometry for tests or hit testing:
const geometry = layout(dsl);
for (const node of geometry.nodes) {
  console.log(node.id, node.x, node.y, node.width, node.height);
}

Exports: render, mount, layout, parseDSL, themeCss, and the THEME_CSS constant.

Theming

The SVG embeds a self-contained stylesheet and uses low-specificity :where() selectors, so host CSS can override any --di-* variable without !important. 

.my-diagram .di-viz {
  --di-canvas-bg: #0b1020;
  --di-stroke-container: #22d3ee;
}

Colors are also emitted as concrete presentation attributes. That keeps rasterizers without CSS-variable support (librsvg, ImageMagick, some SVG-to-PNG pipelines) fully colored. In a non-CSS renderer, theme: "auto" bakes the dark palette; use --theme light for a static light SVG.

diviz/theme.css is generated at build time if you prefer an external stylesheet.

Deliberate limits

  • Shared providers are duplicated per socket. A provider referenced twice is drawn twice with unique instance keys. A true shared-singleton edge notation is not implemented yet.
  • Graphs must be acyclic. Cycles and unreachable blocks are rejected with a descriptive error.
  • One parent per block. A block is either a root or plugged into exactly one socket.
  • Text width is heuristic. Monospace character-width estimates are used instead of DOM measurement. CJK or emoji-heavy labels can overflow.
  • All sockets are on the top edge. Candidate side notches exist, but dependency sockets do not rotate to the sides yet.
  • 5,000-instance safety limit. Guards against exponential growth when shared subtrees are duplicated heavily.
